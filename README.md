# Liquid Glass

Материал Liquid Glass из iOS 26 / macOS 26, повторённый в браузере двумя разными способами.

| Файл | Техника | Чем берёт |
|---|---|---|
| `index.html` | CSS + SVG-фильтры в `backdrop-filter` | Работает поверх обычного DOM, ничего не надо переписывать |
| `webgl.html` | WebGL2, свой фрагментный шейдер | Настоящее преломление по `refract()`, спектральная дисперсия, отражение окружения |
| `blender/glass_ref.py` | Cycles, честная трассировка | Эталон для сверки: как стекло ведёт себя на самом деле |
| `tests.html` | Прогон обеих страниц в скрытых фреймах | 49 проверок и бюджеты по скорости |
| `invariants.html` | Свойства вместо примеров, тысячи случайных случаев | 31 инвариант, ~27 000 случаев за прогон |
| `bench.html` | Таскает панель в видимом фрейме и считает кадры | Во что обходится движение и из чего эта цена состоит |
| `electron/` | Те же страницы как приложение с пятью вкладками | Установщик и портативный exe для Windows, без браузера и без сервера |

Ни в одной странице нет зависимостей и сборки. Открыл файл - работает. Node и Electron нужны только для приложения, страницы о них ничего не знают.

```bash
python -m http.server 8123
```

Потом `http://localhost:8123/index.html`. Открывать через `file://` тоже можно, но фильтры с data-URL надёжнее работают по HTTP.

## Что происходит внутри

Обычный `backdrop-filter: blur()` даёт матовое стекло. У Apple стекло другое: почти прозрачное в середине, а вся работа идёт на кромке. Там фон преломляется, разбивается на цветные каналы и вспыхивает бликом.

Чтобы это повторить, для каждого стеклянного элемента строится поле расстояний (SDF) его собственной формы, из него - профиль высоты кромки, а из профиля - четыре текстуры:

| Текстура | Что в ней | Куда идёт |
|---|---|---|
| `disp` | R и G = смещение выборки фона, B = кольцо кромки | `feDisplacementMap`, плюс распаковка синего в альфу |
| `spec` | белый + альфа по блику | слой `plus-lighter` над элементом |
| `shade` | чёрный + альфа по самозатенению | слой `multiply` над элементом |

Текстур три, а не четыре, и это не косметика. Каждый вызов `toDataURL` стоит около 0.9 мс фиксированно, независимо от размера картинки. `feDisplacementMap` читает только R и G, поэтому синий канал свободен, и маска кромки живёт там. Достаётся она одним `feColorMatrix`, который переносит B в альфу.

Дальше цепочка фильтра: три прохода `feDisplacementMap` с чуть разными масштабами для R, G и B (это и есть хроматическая аберрация), затем выравнивание контраста фона под читаемость текста, затем подмешивание насыщенного кольца по краю.

### Профиль кромки

Ключевая деталь. Если взять `smoothstep`, получится мягкий симметричный бугор - выглядит как подсветка, а не как стекло. Настоящая толстая кромка описывается дугой окружности:

```
h(t) = sqrt(1 - (1 - t)^2),   t = расстояние от контура / ширина фаски
```

У неё производная уходит в бесконечность на самом контуре. Поэтому фон у границы сжимается резко, а к середине искажение исчезает за несколько пикселей. Это и читается глазом как «толстое стекло», а не как «размытие».

### Знак смещения

Тоже важно. Выпуклая кромка работает как линза и **затягивает внутрь то, что снаружи** элемента. Значит масштаб в `feDisplacementMap` отрицательный. С положительным знаком получается обратный эффект: фон растекается наружу, и стекло выглядит как мыльный пузырь.

### Блик

Блик не рисуется градиентом. Он считается по нормали поверхности из того же поля высот: зеркальная составляющая Блинна-Фонга, френель по краю и вторая, более тусклая заливка со стороны, противоположной источнику. Поэтому блик сам огибает углы и даёт характерную двойную кромку - яркую сверху и приглушённую снизу.

### Углы

Если браузер поддерживает `corner-shape: squircle` (Chrome 139+), форма элемента и SDF считаются по суперэллипсу с показателем 4. Кривизна меняется плавно, как у иконок iOS. Без поддержки - обычная окружность, и SDF переключается на неё же, чтобы карта совпала с реальной обрезкой.

## Панель управления

Справа живая панель. Ползунки разделены по стоимости пересчёта: цвет и яркость меняются мгновенно через CSS-переменные, оптика перестраивает только разметку фильтра, геометрия перепекает текстуры.

| Группа | Параметр | Что делает |
|---|---|---|
| Optics | Refraction | Сила преломления на кромке |
| Optics | Edge width | Ширина фаски в пикселях |
| Optics | Chromatic | Расхождение R и B каналов |
| Optics | Rim glow | Насыщенное свечение по краю |
| Optics | Blur | Размытие фона под стеклом |
| Optics | Legibility dim | Приглушение фона ради читаемости текста |
| Light | Light angle | Направление источника света |
| Light | Specular / Self-shadow / Glare | Яркость блика, самозатенения и подвижного пятна |
| Material | Saturation / Tint / Corner radius | Материал стекла |
| Behaviour | 4 переключателя | Аберрация, суперэллипс, пружинная анимация, режим пониженной прозрачности |

Внизу счётчик кадров и переключатель движения обоев.

## Про скорость

Считалось это всё довольно долго, поэтому вот замеры и что с ними сделано. Все цифры для восьми стеклянных элементов при dpr 1, самый крупный из них 210x806.

| | Было | Стало |
|---|---|---|
| Выпечка всех текстур | 249 мс | 71 мс |
| Выпечка одной большой панели | 105 мс | 16 мс |
| Пересборка фильтра на тик ползунка | ~40 мс | 0.5 мс |

Что оказалось дорогим:

Проход освещения занимал 74 мс из 105. Внутренность элемента считалась полностью, хотя она плоская: наклон нулевой, блик нулевой, кольцо нулевое. Теперь на первом проходе для каждой строки запоминается интервал пикселей глубже фаски, и весь этот интервал заполняется одним заранее посчитанным значением. Плюс `Math.hypot` заменён на `sqrt`, а `Math.pow(x, 46)` и `Math.pow(x, 26)` разложены в возведение в квадрат.

Кодирование PNG занимало 76 мс из 108, причём почти не зависело от разрешения. Замер показал ~0.9 мс фиксированных накладных расходов на каждый вызов `toDataURL`. Понижать разрешение бессмысленно, надо резать количество вызовов: четыре текстуры на элемент превратились в три.

Пересборка фильтра заменяла весь узел `<filter>` целиком, а внутри лежали `feImage` с data-URL, которые Chrome декодировал заново. Теперь узел пересобирается только при смене формы цепочки, в остальных случаях правятся атрибуты.

Движение обоев по умолчанию выключено. Восемь кругов с `mix-blend-mode: screen`, ползающих по экрану, каждый кадр инвалидируют фон под всеми стеклянными элементами, а значит все восемь цепочек фильтров обязаны пересчитаться. При неподвижных обоях Chrome просто не перерисовывает то, что не менялось.

Ползунки геометрии (Edge width, Corner radius, Light angle) требуют перепечки текстур. Заказ на перепечку ограничен одним на 90 мс, а после отпускания ползунка обязательно приходит финальная на точном значении.

### Выпечка ушла в воркер

Разбивка на реальном окне 1440x880: из 229 мс выпечки 171 мс приходилось на кодирование PNG, и всё это на главном потоке. Отсюда проседания при любой смене геометрии.

Теперь пиксельная математика остаётся обычной функцией, а исходник воркера собирается через `String(fn)`. Копия кода одна, и воркер исполняет буквально её. Кодирование внутри воркера идёт через `OffscreenCanvas.convertToBlob` и `FileReaderSync`, так что base64 тоже считается не на главном потоке.

| | Было | Стало |
|---|---|---|
| Блокировка главного потока при полной перепечке | 299 мс | 0.4 мс |
| Самая большая панель | 105 мс на главном потоке | 81 мс в фоне |

Две ловушки по дороге. `clamp` и `byte` были стрелочными функциями в `const`, а `String()` от такой даёт анонимное выражение, которое воркер не может вызвать по имени. Пришлось сделать их объявлениями. И упавший воркер оставлял все элементы без карт навсегда, теперь `drainWaiting()` доделывает работу на главном потоке.

### Очередь выпечки не растёт

Ограничение «один заказ на 90 мс» говорило, как часто главный поток просит новые текстуры, и ничего — о том, как быстро воркер успевает их печь. А полный набор из восьми панелей стоит воркеру 90 мс при dpr 1 и около 240 мс при dpr 2. На ноутбуке с масштабированием заказ приходил втрое чаще, чем выполнялся, а `postMessage` нельзя отозвать.

Замер: протаскивание Light angle на 20 шагов ставило в очередь 160 выпечек и разбирало её 3.0 с. Девятнадцать шагов из двадцати — это формы, мимо которых ползунок уже проехал, и каждая из них, вернувшись, ещё и перестраивала цепочку фильтра и заставляла Chrome заново декодировать три PNG. Так это и выглядело как зависание: страница продолжала работать секундами после того, как ползунок отпустили.

Теперь в воркере лежит ровно одна форма, а очередь ключуется **элементом, а не формой**. Разница принципиальная: элемент в каждый момент хочет ровно одну форму, поэтому очередь по построению не может вырасти больше числа панелей на экране — сколько бы ни длилось протаскивание. И обход по кругу делает её честной: очередь по формам обслуживает того, кто попросил раньше, снова и снова, а остальные голодают. На dpr 2 это значило, что пять панелей из восьми переставали обновляться, пока не отпустишь ползунок.

Насос читает у элемента ту форму, которую тот хочет **в момент отправки**, — протухшая задача просто не может возникнуть.

| Протаскивание Light angle, 20 шагов | Было | Стало |
|---|---|---|
| Задач ушло в воркер | 160 | 9 |
| Успокаивается за | 3.0 с | 1.0 с |
| Пик очереди на 8 панелей (60 шагов) | 1297 записей | 17 |

Пик нашёл стенд инвариантов: backpressure ограничил только то, что уходит в воркер, а сами `waiting` и `backlog` продолжали пухнуть, потому что протухшее выбрасывалось лишь тогда, когда до него доберётся насос. Очередь по элементам закрывает и это, и голодание — одним разворотом структуры.

Финальное значение доезжает по-прежнему: на форме, на которой ползунок отпустили, живой `geoSig` есть всегда, поэтому её не выбросят. Последовательная выдача при этом ничего не стоит — восемь выпечек по одной занимают 80 мс против 84 мс, если вывалить их разом.

Одна форма в воркере означает одну форму, способная его заклинить. Отклонённый `convertToBlob` не поднимает `error` на воркере, поэтому воркер теперь отвечает и на неудачу тоже, а задачу, не вернувшуюся за 8 секунд, страница считает потерянной вместе с воркером и допекает остаток сама. И `drainWaiting()` больше не печёт формы, которых никто не ждёт: упасть посреди протаскивания и синхронно испечь все его кадры — то же самое зависание, только на главном потоке.

### Свет не трогает карту смещения

Карта смещения зависит только от геометрии: угол света входит в блик и самозатенение, а `disp` не меняется ни на байт. Это не рассуждение — инвариант `the displacement map does not depend on the light angle` проверяет побитовое совпадение на случайных формах каждый прогон.

Поэтому ключей теперь два. `shapeKey` — геометрия, `bakeKey` — геометрия плюс свет. Из этого следуют две вещи:

- воркер не кодирует и не отправляет карту смещения, если она у страницы уже есть: **42% пакета на каждую выпечку** (12 КБ против 7);
- сигнатура цепочки фильтра ключуется геометрией, а не светом, поэтому протаскивание Light angle **не перестраивает ни одного узла фильтра** — раньше перестраивались все восемь на каждый шаг, и Chrome каждый раз заново декодировал data-URL с картой.

Сигнатура при этом описывает то, из чего цепочка **собрана**, а не то, чего элемент хочет. Разница неочевидная и стоила бага: `sync()` записывает новый ключ сразу, карты приходят позже, и любой `run(2)` в этом промежутке перестраивал цепочку из старых карт, штампуя сигнатуру новой формой. Правильные карты потом приходили к цепочке, которая уже считала себя актуальной, и `feImage` навсегда оставался с чужой картой преломления.

### Пока панель едет, цепочка короче

Перетаскивание панели не печёт ничего — там только `left/top`, пружина и блик. Тормозит оно по другой причине: фон под едущей панелью меняется каждый кадр, а значит цепочка фильтра целиком пересчитывается каждый кадр. И пересчитывается она на CPU: `backdrop-filter` с `blur()` и `saturate()` уходит на GPU, а с `url(#фильтр)`, внутри которого `feImage` и `feDisplacementMap`, — нет.

Замер `bench.html`, тащим одну панель. Числа — медиана трёх кругов, потому что одиночный прогон здесь врёт: три подряд разошлись на одной и той же строке до 2.4× (потолок приходил 239, 239 и 188). Всё, что не выходит за этот разброс, стендом помечается как шум и коэффициентом не притворяется.

| Что рисуем | fps | разброс | вывод |
|---|---|---|---|
| Полная цепочка, упрощение выключено | **33** | 31–40 | это было «до» |
| **Как сейчас** | **121** | 121–199 | **3.7×** |
| + все панели на облегчённой цепочке | 121 | 121–124 | неотличимо от базы |
| + без legibility | 121 | 121–167 | неотличимо: уже снято |
| + refraction 20 | 121 | 119–147 | неотличимо |
| + `will-change: transform` | 197 | 128–212 | единственное, что торчит |
| Вообще без SVG-фильтра | 123 | 121–190 | драг дошёл до потолка |

Две вещи выяснились не сразу.

Первая: **`feComponentTransfer` с таблицей — самая дорогая стадия во всей цепочке.** Ранний замер объявил её бесплатной, но он был грязный: строки, меняющие настройку, звали `run(2)` прямо перед подсчётом, и пересборка восьми цепочек с декодом PNG попадала внутрь окна измерения. Хроматика и rim glow вместе дают около 12%, а одно затемнение — вчетверо.

Вторая, и главная: **при перетаскивании одной панели перефильтровываются все.** У `backdrop-filter` фон — это всё содержимое под элементом внутри его backdrop root, поэтому любое движение там инвалидирует каждый из них. Отсюда и разрыв: облегчить только ту панель, что под курсором, — примерно 1.25×, облегчить все — 5.4×, а отдать неподвижным обычный блюр — ровно потолок, то же число, на котором страница простаивает.

Строка «все панели на облегчённой цепочке» после правки стала показывать **ровно то же, что базовая** — она ведь теперь делает то же самое, что обычный драг. Это и есть подтверждение механизма, более надёжное, чем само число.

Половина строк упирается в одинаковые 121 fps не случайно: на экране 240 Гц это «кадр через раз», и всё, что дешевле этого шага, показывает одно и то же. По той же причине потолок съехал с 239 на 123. Практически это значит, что различать там больше нечего.

Поэтому на время перетаскивания (настоящего — не просто нажатия) со **всех** панелей снимаются все три украшения: **14 примитивов превращаются в 2**. Само преломление остаётся — ровно то, ради чего панель и таскают. Затемнение нужно, чтобы читался текст, а пока стол едет, никто не читает. Блик и самозатенение живут в CSS-слоях `::before` и `::after`, фильтра не касаются, так что материал на месте.

Выключается в панели: **Simplify while moving**. Выключите и потащите панель, глядя на счётчик кадров — разница видна сразу.

Если всё равно тяжело: выключите Chromatic и Rim glow совсем.

### Ветка без SVG-фильтров

Safari и Firefox не умеют `backdrop-filter: url(#фильтр)`, и для них есть запасной путь — обычный `blur + saturate`. Покрытия у него не было вообще, и там нашёлся баг: `provisional()` начинался с `if(!SVG_BACKDROP) return;`. То есть на тех самых браузерах, где плоский блюр — это финальный вид, а не заглушка, элемент оставался вообще без фона, пока не придёт выпечка, которой он всё равно не воспользуется.

`SVG_BACKDROP` теперь `let`, и стенд ходит по этой ветке в браузере, которому она не нужна: проверяет, что ни один элемент не остался ни без фона, ни со ссылкой на фильтр, что свежий элемент без текстур сразу читается как стекло, что предупреждение в панели показывается, и что после возврата всё встаёт на место.

### Инварианты

```
http://localhost:8123/invariants.html
http://localhost:8123/invariants.html?seed=777
```

Не примеры, а свойства. Каждая строка — утверждение, которое обязано выполняться для **любого** входа, и проверяется оно на тысячах случайных. Пиксельная математика чистая, её можно долбить напрямую; очередь выпечки и жизненный цикл стекла — автоматы, им достаются случайные последовательности действий и проверка после того, как всё успокоится. Около 27 000 случаев за прогон, зерно печатается в итоге и подставляется через `?seed=`.

Что проверяется: симметрия и границы `corner()`, знак и монотонность `sdf()`, что самодельные `pow46`/`pow26` действительно равны `x^46` и `x^26`, что текстура не выходит за бюджет пикселей, что каналы не залезают друг в друга, что снаружи формы ничего не нарисовано, что две выпечки одной формы дают одинаковые байты, что при свете строго сверху блик симметричен, и что преломление на противоположных кромках гнёт в разные стороны.

Дальше автоматы: после любой последовательности действий очередь пуста, у каждого видимого элемента есть карты, `feImage` показывает ту карту, которую элемент держит, число узлов в `defs` равно числу элементов, ни один элемент не стоит в очереди дважды, и очередь не перерастает число панелей.

Отдельная группа смотрит на картинку, чего не делает больше ничто: что блик идёт за источником по кругу (0° — справа, 90° — сверху, 180° — слева, 270° — снизу), и что байты шести опорных форм совпадают с зафиксированными контрольными суммами. Поменять математику теперь можно только осознанно — суммы придётся обновить руками.

Ещё одна группа — `webgl.html`: что каждый юниформ, который выставляет кадр, действительно существует в программе (опечатка в имени даёт `null`, и значение молча не доезжает до шейдера), что оба фреймбуфера полные, что целый кадр не поднимает ни одной ошибки GL, что прямоугольники панелей следуют за DOM и что нулевой размер окна ничего не рисует вместо того, чтобы сыпать ошибками.

Стенд оправдался сразу и дважды. Первый прогон нашёл пик очереди в 1297 записей. Второе зерно нашло `paints a displacement map it is not holding` — тот же класс бага, что чинился до этого, но с другого входа, и первое зерно его не поймало.

### Что ещё можно снять — меряется, а не угадывается

```
http://localhost:8123/bench.html
```

Таскает панель в **видимом** фрейме под каждой конфигурацией и считает кадры: полная цепочка, текущая, движение через `transform` вместо `left/top`, без слоёв `::before`/`::after`, с `will-change`, с втрое меньшей областью фильтра, без legibility, и без SVG-фильтра вовсе — это потолок, выше которого на этой технике не прыгнуть.

Окно должно быть на переднем плане и ничем не закрыто. Некомпозитящаяся вкладка паркует `requestAnimationFrame`, и стенд в этом случае ставит прочерк, а не придумывает число.

## Проверки

```
http://localhost:8123/tests.html
```

Обычная страница, грузит обе версии в скрытые фреймы и проверяет 49 вещей: что каждый ползунок доходит до того свойства, которым он якобы управляет, что переключатели переключают именно то, что написано, что меню освобождает свои узлы фильтров, что скрытые элементы не пекутся, что нажатие на кнопку не двигает соседей, что сломанный шейдер показывает лог. Плюс бюджеты по времени.

Отдельно — то, что проверить состоянием нельзя: сколько работы взаимодействие успевает заказать. Стенд протаскивает Light angle на 20 шагов, считает задачи, ушедшие в воркер, и требует, чтобы их было не больше трёх на элемент и чтобы элементы всё-таки остановились на отпущенном значении. Заодно проверяются оба способа потерять воркер: форма, которую он не смог закодировать, и форма, на которую он не ответил вовсе.

Внутрь страниц стенд лезет через `eval` в их собственной области видимости, поэтому ни `index.html`, ни `webgl.html` не носят в себе тестовых заглушек. Фреймы грузятся с меткой времени: стенд, проверяющий закешированную сборку, хуже, чем никакого.

Частота кадров помечается как **skip**, а не выдумывается, когда вкладка не композитится. Браузер в этом случае паркует `requestAnimationFrame`, и любой замер вернёт ноль. Чтобы получить эти цифры, страница должна быть на переднем плане.

Стенд окупился сразу: он показал, что полная выпечка занимает 299 мс на окне 1440x880, тогда как раньше было записано 71 мс, померенное в окне поменьше.

```bash
npm run dist
```

`npm run dist` кладёт оба exe в `dist/`. Приложение делается только под Windows. Сборка под macOS возможна только на самом macOS, настройки для неё лежат в `package.json` на всякий случай.

### Вкладки

Сверху полоска из пяти вкладок: CSS + SVG, WebGL2 | Checks, Invariants, Bench. Каждая вкладка отдельная живая страница. Переключились на WebGL и обратно, а ползунки CSS-версии стоят где стояли, ничего не перезагрузилось. Вкладка создаётся при первом открытии, а не все пять на старте.

Фоновая вкладка для своей страницы скрыта (`visibilityState` равно `hidden`), так что Chromium её не рисует и `requestAnimationFrame` у неё стоит. Отсюда следствие: если уйти со вкладки Checks посреди прогона, замеры частоты кадров там получат skip. Это то же правило, что в обычном браузере: стенд надо держать на переднем плане.

Ссылка внутри страницы (например, «WebGL2 version» в демо) не уводит вкладку на другую страницу, а открывает нужную вкладку. Так каждая вкладка всегда показывает свою страницу.

| Клавиши | Что делают |
|---|---|
| Ctrl+1 … Ctrl+5 | Открыть вкладку по номеру. Работает на любой раскладке, смотрится физическая клавиша, а не символ |
| Ctrl+Tab, Ctrl+Shift+Tab | Следующая и предыдущая вкладка, по кругу |
| Ctrl+PageDown, Ctrl+PageUp | То же самое |
| Ctrl+R, кнопка ↻ справа | Перезагрузить открытую вкладку, остальные не трогаются |
| Ctrl+Shift+I | DevTools открытой вкладки |
| Ctrl+= / Ctrl+- / Ctrl+0 | Масштаб |
| F11 | Полный экран |
| Alt | Показать меню. Оно спрятано, потому что вкладки его заменяют |

На вкладках Checks и Invariants после прогона загорается точка: зелёная, если всё прошло, красная, если что-то упало. Её видно с любой вкладки. Статус берётся из заголовка страницы, стенды пишут туда `ok 49/49`, `FAIL …` или `BROKE …`. Заголовок окна повторяет заголовок открытой страницы.

### Почему свой протокол, а не file://

Первой мыслью было открыть `index.html` через `loadFile`. Но стенды через `file://` не работают: Chromium выдаёт каждому такому документу своё непрозрачное происхождение, и `tests.html` не может залезть во фрейм, который гоняет. Поэтому страницы отдаются через схему `app://glass`, зарегистрированную как стандартная и безопасная. У всех страниц одно происхождение, `isSecureContext` истинно, воркер из blob-адреса запускается, `sessionStorage` в WebGL-версии переживает перезагрузку.

Отдаёт страницы `serve.js`, и путь к файлу из адреса он не строит. Имя после слэша сверяется со списком из пяти страниц, всё остальное получает 404 без обращения к диску. Так что `../package.json`, `%2e%2e/`, `..%5c`, `INDEX.HTML` и любая другая комбинация не дойдут до кода оболочки внутри `app.asar`. Это следует из конструкции, и тесты это проверяют.

Каждая страница приходит с CSP `default-src 'none'`. Разрешено ровно то, чем страницы пользуются: встроенные скрипты и стили, `eval` (им стенды лезут во фреймы), воркер из `blob:`, картинки из `data:` и `blob:` (карты преломления), фреймы только с `app://glass`. Внешних источников в политике нет ни одного, так что приложение физически не может ничего загрузить из сети.

### Проверки оболочки

Два уровня.

`npm test` - 24 теста на обычном Node, меньше секунды. Проверяют свойства, а не примеры:

- 30 000 случайных путей из «опасных» кусков (`..`, `%2e`, `%5c`, `C:`, `%00`, `app.asar`, `package.json`) дают либо страницу из списка, либо ничего;
- 3 000 случайных запросов ни разу не заставляют `respond()` читать файл вне списка;
- политика не содержит ни `http:`, ни `https:`, ни `*`;
- 20 000 случайных нажатий клавиш: без Ctrl или Cmd вкладка не переключается никогда, с отпусканием клавиши, с Alt, с Shift+цифрой тоже никогда, а результат всегда либо вкладка из списка, либо ничего;
- переход по кругу на любой шаг от -1000 до 1000 совпадает с арифметикой по модулю, пять шагов вперёд возвращают на место, шаг назад отменяет шаг вперёд;
- статус вкладки читается ровно из того формата заголовка, который пишут стенды. Тест берёт этот формат из исходника `tests.html` и `invariants.html`, так что если стенд начнёт писать заголовок иначе, упадёт тест, а не тихо погаснет точка.

Отдельно проверяются связи между файлами: каждая `.html` в корне есть в списке и в `build.files`; каждый файл оболочки, каждый `require('./…')` и каждый `path.join(__dirname, …)` попадают в пакет; каждая ссылка вида `'webgl.html'` внутри страниц ведёт на существующую страницу; каждый IPC-канал, который шлёт полоска вкладок, слушается в `main.js`, а каждая функция `shell.*`, которую она зовёт, выставлена в preload.

Тесты проверены мутациями: 25 раз в копию оболочки вносилась поломка. Среди них: отдавать любой путь, не смотреть на хост, сравнивать без учёта регистра, декодировать до сверки, читать файл до проверки, разрешить `https:` картинкам, убрать `no-store` или `worker-src`, переключать вкладку по Alt+цифре, по отпусканию клавиши, по Shift+цифре или вообще без Ctrl, забрать Cmd+Tab у системы, сломать круг на отрицательном шаге, принимать `ok` без счёта, переименовать IPC-канал, потерять `reload` в preload, опечататься в пути к preload, не упаковать `bench.html`, `selftest.js` или `tabs.html`. Все 25 поймал хотя бы один тест.

`npm run selftest` (или собранный exe с флагом `--selftest`) проверяет то, что Node проверить не может, прямо внутри того Chromium, который едет в приложении:

- каждая страница отдаётся с кодом 200 и с политикой, десять вариантов побега получают 404;
- окно открывается на демо с одной вкладкой, остальные ещё не созданы;
- страница живёт в безопасном контексте на `app:`, WebGL2 есть;
- `window.open` отклоняется, переход на внешний адрес отменяется;
- ссылка на другую страницу открывает её вкладку, а исходная вкладка остаётся на своей странице;
- фоновая вкладка видит себя скрытой, а открытая видима ровно настолько, насколько видимо само окно. Сравнивать приходится с окном, а не с «visible»: если окно приложения закрыто другим окном, Chromium считает его скрытым целиком. Первая версия этой проверки падала, стоило открыть поверх что-нибудь ещё. Видимость окна берётся у полоски вкладок, она живёт в том же окне;
- метка, оставленная в `window`, переживает уход на другую вкладку и возврат, то есть ничего не перезагрузилось;
- кнопка ↻ перезагружает открытую вкладку и не трогает соседнюю;
- после ресайза до 900x640, 520x400 и обратно полоска и страница стоят ровно на своих местах;
- на вкладках Checks и Invariants после прогона горит правильная точка;
- в меню Pages у каждой вкладки своё сочетание, от Ctrl+1 до Ctrl+5;
- 150 случайных переключений всеми способами сразу: клик по вкладке, Ctrl+цифра в странице, Ctrl+Tab и Ctrl+Shift+Tab, Ctrl+PageUp/PageDown в полоске, пункт меню, ссылка внутри страницы. После каждого шага открытая вкладка сверяется с моделью, а затем проверяется всё, что обязано держаться: видна ровно одна вкладка и это открытая, каждая вкладка на своей странице, полоска отмечает ровно открытую, заголовок окна равен заголовку страницы, размеры сходятся с окном;
- контроль: внешняя картинка должна быть отклонена политикой, и слушатель это видит. Только после этого его молчание на остальных страницах что-то значит;
- `tests.html` и `invariants.html` проходят целиком;
- `bench.html` дотягивается до своего фрейма;
- политика не отклонила ничего, что нужно страницам, и ни один запрос не ушёл за пределы машины.

Результат на Electron 44.3.0 / Chromium 152 одинаковый из исходников, из собранного `win-unpacked` и из установленной версии: 49 проверок из 49, 31 инвариант на 27 383 случаях, 150 случайных переключений без расхождений, отказов политики 0, внешних запросов 0. Полный прогон занимает около 27 секунд. Код выхода 0 или 1, так что это можно гонять в CI.

Портативный exe для этого не годится. Его обёртка ждёт приложение, но не передаёт ни вывод, ни код выхода: приложение, убитое с кодом -1, обёртка отчитала как 0. Для самопроверки берите `dist/win-unpacked/Liquid Glass.exe --selftest` или установленную версию.

Снаружи, настоящими нажатиями и настоящим установщиком, проверено ещё вот что:

- тихая установка `/S` ставит приложение для текущего пользователя, пишет запись «Liquid Glass 1.0.0» в HKCU, кладёт ярлыки в меню Пуск и на рабочий стол; тихое удаление убирает exe, запись, ярлыки и папку целиком;
- Ctrl+2, Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+PageUp, Ctrl+5 и Ctrl+1, нажатые по-настоящему, открывают те вкладки, которые обещаны, заголовок окна меняется следом;
- Ctrl+R перезагружает открытую вкладку при включённой русской раскладке. Первая попытка проверить это через `SendKeys('^r')` провалилась: `SendKeys` ищет букву «r» в текущей раскладке, а в русской её нет. Настоящая клавиша R работает на любой раскладке, так что проверка теперь жмёт виртуальный код клавиши;
- F11 разворачивает окно ровно на экран 1920x1080, повторное F11 возвращает его точно на прежнее место;
- второй запуск выходит за секунду, окно остаётся одно; после закрытия окна не остаётся ни одного процесса.

Окно при самопроверке должно быть видно и ничем не закрыто: частота кадров меряется по `requestAnimationFrame`, а свёрнутому или закрытому другим окну Chromium его не даёт. В таком случае замеры кадров получают skip, а самопроверка пишет, что окно закрыто. Две самопроверки сразу тоже мешают друг другу: окна перекрываются.

У самопроверки своя папка профиля во временном каталоге. Она не трогает настоящий профиль и не спорит за кеш с открытым рядом приложением.

## Файлы

<details>
<summary><b>index.html</b> - весь проект, ~1850 строк</summary>

Один файл: разметка, стили и движок. Разделы внутри:

<details>
<summary>CSS: <code>:root</code> и переменные</summary>

Все настраиваемые величины живут в CSS-переменных на `:root`: `--rad-base`, `--blur`, `--sat`, `--tint`, `--spec`, `--shade`, `--glare`. JS их переписывает, когда двигаете ползунки «дешёвой» группы. Ничего пересчитывать не нужно, браузер сам перерисует.
</details>

<details>
<summary>CSS: <code>#wall</code> и фон</summary>

Фон намеренно контрастный: радиальные градиенты, восемь плавающих кругов в режиме `screen`, сетка 44px, полосы и повторяющийся текст. Без резких границ преломление просто не видно - размывать нечего.

Круги медленные (26-56 секунд). Каждый кадр их движения заставляет браузер пересчитывать `backdrop-filter` всех стеклянных элементов, так что это самая дорогая часть демо.
</details>

<details>
<summary>CSS: <code>.lg</code> - базовый класс стекла</summary>

Даёт скругление, лёгкую белую подложку `--tint`, две тени и `isolation: isolate`. Трансформация собрана из переменных: `--bx/--by` для базового сдвига (док центрируется через `-50%`) и `--sx/--sy` для пружинного сжатия при перетаскивании.

`.lg::before` - аддитивный слой, `mix-blend-mode: plus-lighter`. В нём две картинки: подвижное пятно-блик радиальным градиентом и запечённая карта `--spec-map`.

`.lg::after` - вычитающий слой, `mix-blend-mode: multiply`, карта `--shade-map`.

`.lg > *` получает `z-index: 3`, чтобы содержимое не оказалось под слоем теней.
</details>

<details>
<summary>CSS: компоненты</summary>

Часы, карточка плеера, тулбар (кнопка-капсула, сегментированный контрол, переключатель, слайдер), док, панель управления, контекстное меню. Каждый задаёт свой `--radius`; капсулы получают `999px`, и движок сам переключает их на круглые углы вместо суперэллипса.

В конце три брейкпоинта: 1240, 900 и 680 пикселей.
</details>

<details>
<summary>JS: <code>corner()</code> и <code>sdf()</code></summary>

`corner(a, b, n)` - n-норма. При `n = 2` это обычный `hypot`, то есть круглый угол. При `n = 4` получается суперэллипс, то есть «непрерывный» угол в стиле Apple.

`sdf()` - знаковое расстояние до скруглённого прямоугольника. Отрицательное внутри, положительное снаружи. Из него берётся всё остальное.
</details>

<details>
<summary>JS: <code>bake()</code> - выпечка текстур</summary>

Главная функция. Считает поле высот `H`, нормализованное расстояние `T`, маску сглаживания `A`, затем в одном проходе выдаёт четыре `ImageData` и превращает их в data-URL.

Смещение кодируется через `tanh`, а не обрезанием по 255. Обрезание дало бы плоское кольцо постоянной силы; `tanh` сжимает мягко и сохраняет градиент.

Градиент домножается на ширину фаски, поэтому он безразмерный. Практический смысл: меняете Edge width - меняется только ширина полосы, а сила преломления остаётся прежней.

Результат кешируется по ключу `размер:радиус:фаска:показатель:угол света`. Восемь элементов с одинаковыми размерами делят одну текстуру. Кеш чистится после 90 записей.

Разрешение ограничено 1.4 млн пикселей: очень большая панель печётся с пониженным DPR, иначе `toDataURL` начинает подтормаживать.
</details>

<details>
<summary>JS: <code>filterMarkup()</code></summary>

Собирает `<filter>` строкой. Порядок: карта смещения → три (или один) прохода `feDisplacementMap` → `feComponentTransfer` для читаемости → насыщенное кольцо через `feComposite operator="in"`.

Область фильтра задана в `userSpaceOnUse` с полем ровно под максимальное смещение, а не процентами. Для панели 272x740 это примерно вдвое меньше обрабатываемых пикселей, чем при `-35% / 170%`.

Терминирующего примитива нет намеренно: SVG берёт результатом вывод последнего примитива в документе.
</details>

<details>
<summary>JS: класс <code>Glass</code></summary>

Обёртка над элементом. `metrics()` берёт `offsetWidth/offsetHeight`, а не `getBoundingClientRect` - иначе пружинное сжатие попало бы в размер текстуры и та бы дрожала.

`sync()` перепекает карты только при смене подписи геометрии. `optics()` пересобирает фильтр. `relight()` пересчитывает положение блика от положения элемента на экране: свет принадлежит комнате, а не элементу, поэтому при перетаскивании пятно скользит по стеклу.

`step()` - пружина по времени, а не по кадрам. Если вкладка была свёрнута и `requestAnimationFrame` замирал, элемент не останется деформированным.
</details>

<details>
<summary>JS: <code>refresh(level)</code></summary>

Три уровня. `1` - только CSS-переменные. `2` - пересборка разметки фильтра. `3` - полная перепечка текстур. Всё складывается в один `requestAnimationFrame`, поэтому таскание ползунка не запускает десятки перепечек подряд.
</details>

<details>
<summary>JS: перетаскивание</summary>

`pointerdown` фиксирует элемент по текущим координатам, переводит в `position: fixed` и обнуляет базовый сдвиг. Дальше отслеживается скорость: по ней элемент растягивается вдоль движения и сжимается поперёк, а блик уезжает. На отпускании пружина возвращает `1, 1` с перелётом.
</details>

<details>
<summary>JS: меню</summary>

`spawnMenu()` создаёт новый стеклянный элемент, регистрирует его в движке и запускает FLIP-морфинг: меню стартует из прямоугольника нажатой иконки и разворачивается пружинным кубическим безье с лёгким перелётом по осям. Пункты выезжают каскадом с шагом 28 мс.

Меню - полноценный `.lg`, со своей запечённой картой. При закрытии фильтр удаляется из `<defs>`.
</details>

<details>
<summary>JS: остальное</summary>

Часы, генератор обоев с тремя палитрами, тосты, счётчик кадров, обработчик `resize` с задержкой 140 мс.
</details>

</details>

<details>
<summary><b>webgl.html</b> - версия на WebGL2, преломление считается по-настоящему</summary>

Тот же интерфейс, но стекло рисует фрагментный шейдер. Разметка отвечает только за текст и ползунки: DOM держит раскладку, а шейдер каждый кадр читает прямоугольники элементов и рисует под ними стекло.

<details>
<summary>Чем принципиально отличается от CSS-версии</summary>

В `index.html` преломление имитируется: карта смещения задаёт, откуда брать пиксель фона, и подбирается на глаз.

Здесь считается физика. Из SDF берётся нормаль поверхности, дальше `refract(I, N, 1.0/ior)` с настоящим показателем преломления, луч идёт сквозь стекло заданной толщины и попадает туда, куда попадает. Толщина и IOR - реальные параметры, а не абстрактная «сила эффекта».

Дисперсия тоже честная. Вместо трёх сдвинутых каналов R, G и B идёт цикл по 14 длинам волн: для каждой свой IOR, свой луч, свой отсчёт, и всё это взвешивается обратно в RGB по приближению спектральной чувствительности. На выходе плавная радуга по кромке, а не три полосы.

Плюс появляется отражение окружения, которого в CSS нет в принципе. Френель по нормали смешивает преломлённый фон с аналитическим окружением (небо, источник света, заполняющий свет с обратной стороны). Именно оно и подсвечивает всю кромку целиком, а не только точку зеркального блика.
</details>

<details>
<summary>Проходы рендера</summary>

1. Обои. Статичная 2D-канва (сетка, повторяющийся текст, эмодзи - то, что шейдером не нарисуешь) загружается текстурой один раз, поверх в шейдере добавляются подвижные цветные пятна.
2. Стёкла, по одному на панель, сзади наперёд. Каждая панель читает результат предыдущей, поэтому стекло над стеклом работает правильно.
3. Копия финального буфера на экран.

Читать и писать одну и ту же текстуру нельзя, поэтому два фреймбуфера меняются местами. Копирование между ними идёт через `blitFramebuffer`, это прямой GPU-копир, а не полноэкранный квад.
</details>

<details>
<summary>Фрагментный шейдер стекла</summary>

`pnorm` и `sdRect` - то же поле расстояний, что в CSS-версии, с n-нормой для суперэллипса. `sdGrad` берёт градиент конечными разностями, четыре дополнительных вызова на пиксель.

Профиль кромки - та же дуга окружности. Важная деталь: дуга поднимается на всю ширину фаски, поэтому ширина сокращается в производной. Если поделить наклон на ширину фаски (легко ошибиться), нормаль почти не наклоняется и преломление даёт сдвиг в один пиксель вместо десятков.

Блик собран из трёх частей: зеркальный по полувектору с показателем из шероховатости, отражение окружения через френель и отдельный тонкий хайлайт на самом контуре. Последний нужен потому, что реальная кромка там тоньше пикселя, а свет она ловит всегда.

Тень рисуется тем же проходом: снаружи фигуры считается то же поле расстояний со смещением от источника света.
</details>

<details>
<summary>Панель управления</summary>

Ползунки другие, чем в CSS-версии, потому что параметры физические: IOR, толщина стекла, шероховатость, сила отражения, число спектральных отсчётов.

Спектральные отсчёты - главный регулятор цены кадра. 14 штук по умолчанию, каждый это отдельная выборка текстуры. На единице дисперсия пропадает совсем, на 32 кромка становится гладкой радугой.
</details>

<details>
<summary>Холостые кадры и потеря контекста</summary>

Если движение обоев выключено и никто ничего не трогает, рисовать нечего. Флаг `dirty` взводится указателем, вводом и изменением размера, иначе кадр пропускается целиком.

Потерю контекста WebGL (перезапуск драйвера, переключение GPU) страница ловит: настройки уходят в `sessionStorage`, а на событие восстановления страница перезагружается и возвращает их. Без этого оставалась чёрная страница навсегда.
</details>

<details>
<summary>Что не работает и почему</summary>

Шейдер видит только то, что нарисовано в канвасе. Текст и иконки лежат в DOM поверх канваса, поэтому стекло их не преломляет. Обойти это в вебе нельзя: доступа к отрендеренному DOM из шейдера нет.

На практике это не мешает: в iOS содержимое, лежащее на стекле, тоже не искажается. Гнётся только фон.
</details>

</details>

<details>
<summary><b>blender/glass_ref.py</b> - физический эталон в Cycles</summary>

Собирает сцену с нуля и рендерит, ничего не открывая в интерфейсе. Запускать фоном: `blender -b -P blender/glass_ref.py`.

`squircle_outline` - контур скруглённого прямоугольника, углы по n-норме, обход против часовой стрелки. `slab` - разворачивает контур в объём: кольца вершин по эллиптической дуге кромки сверху, прямая стенка, зеркальная кромка снизу. Вдвижение каждого кольца считается как контур меньшего размера, а не смещением по нормалям.

`glass_material` - три Glass BSDF с разными IOR, окрашенные в чистые каналы и сложенные Add Shader.

`backdrop_material` - цветной градиент с сеткой из тонких линий. Без резких границ преломление не на чем показать.

Режимы: без флагов один кадр `medium`, `--sweep` три варианта глубины кромки, `--solid` матовый отладочный рендер.

Результаты в `blender/out/`.
</details>

<details>
<summary><b>electron/main.js</b> - окно, вкладки, меню, протокол</summary>

Регистрирует схему `app://glass` и отдаёт через неё страницы. Окно - `BaseWindow` под размер рабочей области (не больше 1440x900). ## Эталон из Blender

В папке `blender/` лежит скрипт, который собирает ту же геометрию в Cycles и считает настоящее преломление. Нужен он для сверки: веб-версии подгонялись на глаз по памяти о скриншотах iOS, а тут видно, как ведёт себя стекло на самом деле.

```bash
blender -b -P blender/glass_ref.py -- --sweep
```

Скрипт строит суперэллипс в плане и эллиптическую кромку, тот же профиль, что считает шейдер. Стекло разложено на три Glass BSDF с разными показателями преломления, окрашенных в чистые R, G и B: в Blender 5.2 у Principled BSDF входа Dispersion больше нет, так что дисперсия собирается вручную. Это ровно то же, что делает WebGL-версия, только три длины волны вместо четырнадцати.

Тонмаппинг принудительно выставлен в `Standard`. По умолчанию Blender использует AgX, который заметно гасит насыщенность, а страницы, с которыми идёт сравнение, рисуются в чистом sRGB.

Развёртка даёт три кадра:

| Файл | Глубина кромки / зазор до фона | Что показывает |
|---|---|---|
| `glass_thin.png` | 0.035 / 0.03 | Физически тонкий лист поверх контента. Почти не искажает |
| `glass_medium.png` | 0.09 / 0.10 | Ближе всего к тому, как выглядит iOS |
| `glass_ui.png` | 0.16 / 0.22 | Кромка заметно преувеличена, дисперсия хорошо видна |

Главный вывод сверки: **честно тонкое стекло почти ничего не гнёт**. Чтобы получить узнаваемый ободок, глубину кромки и расстояние до контента приходится задирать далеко за физически осмысленные для накладной панели значения. То есть эффект Apple не физичный, он художественный, и подгонять веб-версию под настоящую физику смысла нет.

Что подтвердилось из того, что делают веб-версии:

- Середина панели прозрачна и не искажает ничего. Плоская пластина, смотришь перпендикулярно - лучи идут насквозь. Обе веб-версии так и делают.
- В ободок затягивается то, что снаружи элемента, сжатое. На рендере видно вторую, сплюснутую копию слова над панелью.
- Цветная бахрома появляется только на кромке и нигде больше.

Что пришлось поправить в скрипте по дороге, если будете его читать:

- Обход контура соединял правый конец одного угла с левым концом другого, то есть вёл рёбра по диагонали через фигуру. Получался параллелограмм с оторванными углами.
- Вдвижение контура по численным нормалям пересекалось само с собой на стыке дуги и прямого участка. Для скруглённого прямоугольника вдвижение считается точно: это просто прямоугольник поменьше.
- Кромка как честная четверть окружности делает поверхность вертикальной у самого контура. Лучи уходят по касательной мимо фона, и край чернеет от полного внутреннего отражения. Ширина и высота кромки должны задаваться независимо.

Флаг `--solid` рендерит ту же сцену матовым материалом. Стекло прячет ошибки геометрии за преломлением, так что при странностях смотреть надо сначала туда.

## Насколько это похоже на оригинал

Сверка с рендером в Blender подтвердила четыре вещи: кромка затягивает внутрь сжатую копию того, что снаружи элемента; середина панели прозрачна и ничего не искажает; цветная бахрома живёт только на кромке; блик, посчитанный из нормалей, сам огибает углы.

Поверх этого доделано то, что отличает живой материал от красивого стоп-кадра.

**Морфинг формы.** Меню больше не просто увеличивается. Из иконки вытягивается капля: два круга под фильтром «размытие плюс крутая альфа-рампа» сливаются в одно тело и перещипываются по мере расхождения. Читается как жидкость именно слияние и разрыв, масштабирование этого не даёт.

**Адаптивное затемнение.** Было линейное приглушение, одинаковое для всего кадра, и оно не могло быть правильным одновременно на светлом и на тёмном фоне. Стало кривой: тёмный конец приподнимается, светлый давится. В CSS-версии это таблица в `feComponentTransfer`, то есть попиксельно и внутри одной панели тоже. В WebGL пересчитывается яркость с сохранением тона.

**Наклон устройства.** На телефоне блик следит за гироскопом. В CSS-версии наклон двигает только подвижное пятно, но не угол света: угол запечён в текстуры, и менять его на каждое показание датчика значило бы перепекать всё. В WebGL угол это просто юниформа, поэтому там наклон крутит его напрямую.

Чего по-прежнему нет:

- Результат ни разу не сверялся с настоящим скриншотом iOS 26. Blender подтвердил физику, но не художественное решение Apple. Это главная оговорка.
- Реакции на прокрутку. В iOS кромка меняется, когда под стеклом едет контент. В демо прокручиваемого контента нет.
- Паритета интерфейса у WebGL-версии: там нет контекстного меню, меню на иконках дока и тостов.
- Работы с клавиатуры: панели нельзя таскать без мыши, у стеклянных элементов нет видимого фокуса.

## Где Liquid Glass получается реалистичнее

Веб - не лучшая площадка для этого эффекта. Ограничение принципиальное: `backdrop-filter` даёт доступ к фону только через фиксированный набор SVG-примитивов. Нельзя написать свой шейдер, нельзя честно посчитать преломление по закону Снеллиуса, нельзя взять размытое мип-отражение окружения.

По убыванию реализма:

**SwiftUI на iOS 26 / macOS 26.** Оригинал. `.glassEffect()`, `GlassEffectContainer`, `glassEffectID` для морфинга между элементами. Считается на Metal на уровне композитора, имеет доступ к настоящему буферу фона и к датчикам наклона. Ничего ближе к «оригинальным эффектам» не существует, потому что это и есть оригинал.

**WebGPU или WebGL.** Полный контроль. Можно взять реальный IOR, посчитать преломление на пиксель по SDF, добавить дисперсию по длине волны, GGX-блик, отражение окружения из кубмапы, размытие по мип-цепочке. Ограничение одно: фон должен быть текстурой. То есть или вся сцена рисуется в WebGL, или фон предварительно рендерится в канвас. Обычный DOM под стеклом так не подложить.

**Android, AGSL.** `RuntimeShader` в `RenderEffect` (API 33+), в Compose через `Modifier.graphicsLayer`. Шейдер получает содержимое слоя под собой. Возможностей почти как в WebGL, и это работает поверх обычного UI. Библиотека Haze делает это из коробки.

**Flutter.** `BackdropFilter` плюс `FragmentProgram` на Impeller. Свой GLSL поверх настоящего фона, кроссплатформенно. Есть готовые пакеты вроде `liquid_glass_renderer`.

**Unity / Unreal / любой 3D-движок.** Grab pass и преломление - штатная функция материала. Реалистичность максимальная, но это уже не интерфейс.

**Веб на CSS и SVG.** Это `index.html`. Потолок такой: смещение по карте, разделение каналов, запечённое освещение. Дальше упирается в отсутствие программируемого шейдера. Выглядит убедительно, но физики в этом нет - только её имитация.

Практический вывод. Если цель - интерфейс приложения под Apple, берите SwiftUI, там всё готово. Если нужен веб и важна достоверность - `webgl.html`, но фон придётся рисовать в тот же канвас. Если нужен веб поверх обычного DOM без переписывания вёрстки - `index.html`, это потолок.
